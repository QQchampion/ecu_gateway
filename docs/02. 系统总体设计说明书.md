# 系统总体设计说明书

System High-Level Design Specification

V1.0 · 总体设计评审版

| **文档属性** | **说明**                                                   |
|--------------|------------------------------------------------------------|
| 项目定位     | 以 Linux 车载通信网关为核心，使用三类 ECU 构建通信管理原型 |
| 适用阶段     | 总体设计；作为详细设计与实现阶段的输入                     |
| 基础实施环境 | Windows + WSL2 Ubuntu + 正点原子 STM32F103 开发板          |
| 当前重点     | 接收、解析校验、路由转发、通信管理、状态监测               |
| 版本状态     | 已确认总体方向，协议与线程等细节待详细设计                 |

**设计主线** 网关是项目主体；三个 ECU 提供业务场景；STM32 负责真实硬件交互。

# 1. 文档目的与设计范围

本文记录已讨论确认的系统总体设计，包括整体部署、节点职责、模块边界、主要数据流、开发技术与演进路径，为后续通信协议、线程模型和接口的详细设计提供依据。

本阶段回答“系统由哪些部分组成、彼此如何协作”，不规定具体报文字节、类接口、线程数量、调度算法或性能阈值。

# 2. 系统总体架构

系统由一个 Linux 网关、三个逻辑独立的 ECU 节点，以及独立日志服务构成。首期动力 ECU、仪表 ECU 为 Linux 软件模拟进程；BCM ECU 运行于真实 STM32 开发板。

**关键约束** ECU 之间不直接交换业务数据；跨 ECU 的数据必须经 Linux 网关路由。独立逻辑网络不等同于现阶段已经具备三条独立物理总线。

# 3. 系统节点与职责

| **节点**      | **部署方式**                     | **主要职责 / 业务方向**                                                                      |
|---------------|----------------------------------|----------------------------------------------------------------------------------------------|
| 动力 ECU      | WSL2 中独立 C++ 进程（TCP）      | 模拟车速、发动机转速、冷却液温度及动力运行状态；以主动上报为主。                             |
| BCM ECU       | STM32F103 开发板（UART）         | 车门、车灯状态管理；执行经网关转发的近光灯、远光灯、左右转向灯控制指令；可辅助使用本地按键。 |
| 仪表 ECU      | WSL2 中独立 C++ 进程（TCP）      | 接收动力和车身数据，命令行显示车辆状态与文字告警；不主动控制其他 ECU。                       |
| Linux Gateway | WSL2 中独立 C++ 进程             | 数据接收、校验、统一消息处理、路由转发、通信管理、状态监测。                                 |
| Logger        | WSL2 中独立 C++ 进程             | 通过本地 IPC 接收运行与异常事件，记录日志；同时作为 IPC 实践模块。                           |
| 控制终端      | 基础阶段为命令行测试端；后续 GUI | 提供经网关转发的 BCM 远程控制请求；后续可视化监控。                                          |

# 4. Linux 网关逻辑分层

| **层次**   | **职责边界**                               | **典型处理**                                              |
|------------|--------------------------------------------|-----------------------------------------------------------|
| 通信接口层 | 不同通信接口的字节收发与传输层面检查       | TCP / UART 接入、帧完整性、长度与基础校验；后续适配 CAN。 |
| 核心业务层 | 统一消息、业务合法性、路由与转发、通信规则 | 检查来源与目标及业务许可，选择目标 ECU 和转发路径。       |
| 设备管理层 | ECU 状态管理、超时与异常事件处理           | 在线 / 离线状态、最近有效通信时间、异常记录与通知。       |

通信接口层将不同介质收到的合法完整报文转化为统一内部消息；业务层基于消息内容进行路由，不应依赖具体接入介质。设备管理层依据有效通信和异常事件维护状态，不要求每条报文顺序经过三层。

# 5. 通信与数据处理设计

## 5.1 通信接口选型

| **连接关系**     | **初期方式**              | **后续演进**                    |
|------------------|---------------------------|---------------------------------|
| 动力 ECU ↔ 网关  | TCP Socket                | 可适配 SocketCAN 或真实车载网络 |
| 仪表 ECU ↔ 网关  | TCP Socket                | 可适配 SocketCAN 或真实车载网络 |
| STM32 BCM ↔ 网关 | UART 串口                 | CAN 收发器与实际总线联调        |
| Gateway ↔ Logger | Unix Domain Socket（IPC） | 根据吞吐及故障恢复需要优化      |

TCP 模拟节点运行在同一 Linux 环境，但作为不同进程维护独立连接与节点身份；不同逻辑网络的物理隔离需在后续硬件阶段验证。

## 5.2 统一消息与转发逻辑

处理路径：接口接收 → 帧完整性与传输合法性检查 → 统一内部消息 → 业务权限与路由校验 → 目标接口发送。

内部消息在总体设计层只要求能够区分来源 ECU、目标 ECU、业务类型和有效负载；字段与序列化规则留待详细设计。

## 5.3 三条典型业务流程

- 动力数据上报：动力 ECU → 网关 → 仪表 ECU；仪表显示车速、转速和温度。

- 车身状态上报：BCM ECU → 网关 → 仪表 ECU；仪表显示车门、车灯状态及文字告警。

- 远程车灯控制：命令行控制端 → 网关 → BCM ECU；BCM 执行后反馈结果与实际状态。

# 6. 进程与并发架构

系统采用多进程组织：Gateway、Power ECU、Cluster ECU、Logger 相互独立；BCM 在 STM32 上运行。Gateway 内部采用事件驱动与多线程配合的思路。

| **构成**     | **总体设计职责**                                                          |
|--------------|---------------------------------------------------------------------------|
| TCP 事件处理 | 使用 Socket + epoll 监听多连接的可读、可写等事件，尽量避免阻塞接收。      |
| 串口通信     | 使用独立执行路径处理 STM32 的 UART 收发，避免拖慢 TCP 接入。              |
| 业务处理     | 通过线程安全、有界的消息队列交接待处理报文；解析、路由和转发与 I/O 解耦。 |
| 设备状态管理 | 跟踪 ECU 有效通信与心跳事件，对超时和异常做状态更新。                     |
| 独立日志     | Gateway 经 Unix Domain Socket 向 Logger 提交日志事件。                    |

**并发原则** 初期保持有界 FIFO 顺序处理；优先级调度属于待评估选项，必须保证同一业务链路的必要顺序。队列只能缓冲突发流量，不能消除持续过载。

# 7. 错误处理与质量目标

| **质量维度** | **总体要求**                                                               |
|--------------|----------------------------------------------------------------------------|
| 通信可靠性   | 检测连接断开、通信超时和异常报文；可恢复时允许节点恢复通信。               |
| 实时性       | 车辆状态上报和车灯控制具备合理响应时效；定量延迟指标待测定。               |
| 系统稳定性   | 异常输入、节点离线及短时流量突发不应直接引发网关崩溃；队列需有容量边界。   |
| 可扩展性     | 新 ECU、CAN 接口和 PC 监控功能尽量通过新增模块接入，降低对路由核心的改动。 |

异常报文处理分层：通信接口层拒绝无法正确成帧或校验失败的数据；业务层拒绝非法来源、目标或不被许可的指令；设备管理层统计异常并更新状态。TCP 数据暂未收完整时应缓存等待，不应误判为非法。

动力 ECU 断开后，网关应将其标记为离线并通知仪表 ECU；仪表端将相关数据标记为无效，避免继续使用过期车速。

# 8. 开发环境与阶段演进

| **阶段**     | **实施内容**                                                     | **重点**                                           |
|--------------|------------------------------------------------------------------|----------------------------------------------------|
| 基础功能阶段 | WSL2 Linux 网关 + 动力/仪表模拟进程 + 真实 STM32 BCM；命令行控制 | 五项网关核心功能；TCP、UART、IPC；联调与异常处理。 |
| 功能完善阶段 | 增加 PC 监控界面与数据可视化                                     | 远程操作与运行可观测性。                           |
| 高级扩展阶段 | 根据条件增加 CAN / SocketCAN、多 ECU 硬件节点、诊断及安全机制    | 多协议与软硬件协同。                               |
| 部署扩展阶段 | 有条件时移植到 ARM Linux 开发板                                  | 真实嵌入式 Linux 环境验证。                        |

当前 WSL2 Ubuntu 属于 Linux 软件开发与联调环境，不等同于已完成嵌入式 Linux 开发板部署。USB 串口能否透传给 WSL2 需要在实施前验证；必要时调整串口接入方案。

# 9. 后续详细设计待定事项

- 通信协议：TCP 与 UART 帧格式、字段类型、校验算法、指令与应答规则。

- 报文路由：ECU ID、业务消息类型、转发映射及业务权限。

- 并发机制：线程数量、队列容量、处理顺序、背压与超时策略。

- 状态机：ECU 在线/离线判据、心跳周期、重连与错误恢复方式。

- 接口规范：模块函数接口、公共消息结构、日志 IPC 格式。

- 验收方式：功能用例、异常用例、稳定性测试方法及量化指标。

# 10. 总体设计评审结论

总体架构能够覆盖已确认的五项网关核心功能，突出 Linux 系统编程与通信转发能力，并通过真实 STM32 BCM 实现硬件交互。项目以通信网关为主、ECU 业务为辅，避免将车身控制或 UI 设计变成主要工作量。

**下一步** 以本文件 V1.0 为基线，进入通信协议与模块接口详细设计；设计调整可更新版本，不必在总体设计阶段提前固定代码实现。
