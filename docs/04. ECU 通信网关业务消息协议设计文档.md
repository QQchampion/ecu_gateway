# ECU 通信网关业务消息协议设计文档

**文档版本：** V1.0
**项目名称：** ECU Communication Gateway
**所属阶段：** M3 业务消息设计
**文档状态：** 第一版设计基线

---

## 1. 项目概述

本项目基于 C++17 和 Linux 开发，实现不同 ECU 设备之间的通信与消息转发。

本阶段主要设计应用层业务消息协议，规定设备编号、消息格式、消息类型、业务数据及设备状态管理规则。

业务消息采用 JSON 格式，外层继续使用 M2 阶段实现的 TCP 长度前缀协议进行传输。

## 2. ECU 设备编号

项目目前定义五种设备：

|设备 ID|设备名称|主要职责|
|---|---|---|
|0x01|Power ECU|动力系统数据采集|
|0x02|BCM ECU|车身控制，如车灯控制|
|0x03|Cluster ECU|仪表显示|
|0x04|Gateway|通信网关，负责消息接收、校验和路由|
|0x05|External Client|外部控制客户端|

## 3. 统一业务消息结构

所有业务消息采用统一的五字段结构：

```
{
  "src_id": 1,
  "dst_id": 3,
  "msg_type": 1,
  "seq": 1001,
  "payload": {}
}
```

### 3.1 公共字段定义

|字段|数据类型|含义|
|---|---|---|
|src_id|Integer|消息发送方设备 ID|
|dst_id|Integer|消息目标设备 ID|
|msg_type|Integer|消息类型|
|seq|Integer|消息序号|
|payload|Object|实际业务数据|

说明：

- `src_id` 用于识别消息来源。

- `dst_id` 用于确定最终接收设备。

- `msg_type` 用于区分不同业务消息。

- `seq` 用于消息识别、顺序辅助判断及请求响应匹配。

- `payload` 用于承载具体业务数据。


## 4. 消息类型定义

第一版定义四种业务消息：

|消息类型|数值|作用|
|---|---|---|
|STATUS|0x01|车辆状态上报|
|CONTROL_REQ|0x02|控制请求|
|CONTROL_RESP|0x03|控制响应|
|HEARTBEAT|0x04|心跳消息|

JSON 中使用十进制数字表示，例如 `0x01` 对应 `1`。

---

## 5. STATUS：车辆状态上报

### 5.1 消息说明

Power ECU 定期向 Cluster ECU 上报车辆状态。

Gateway 接收消息后，根据 `dst_id` 将消息转发给 Cluster ECU。

### 5.2 上报规则

|项目|设计|
|---|---|
|发送设备|Power ECU（0x01）|
|目标设备|Cluster ECU（0x03）|
|消息类型|STATUS（0x01）|
|上报周期|1 秒|
|上报方式|完整状态上报|
|消息序号|每条新消息递增 1|

每次上报均携带完整的四项车辆状态，不采用增量上报。

### 5.3 Payload 定义

|字段|数据类型|单位|示例|
|---|---|---|---|
|speed_kmh|Number|km/h|60|
|rpm|Integer|r/min|2000|
|coolant_temp_c|Number|℃|85|
|engine_status|String|无|RUNNING|

发动机状态定义：

|状态|含义|
|---|---|
|STOPPED|发动机停止|
|STARTING|发动机启动中|
|RUNNING|发动机正常运行|
|FAULT|发动机故障|

### 5.4 消息示例

```
{
  "src_id": 1,
  "dst_id": 3,
  "msg_type": 1,
  "seq": 1001,
  "payload": {
    "speed_kmh": 60,
    "rpm": 2000,
    "coolant_temp_c": 85,
    "engine_status": "RUNNING"
  }
}
```

## 6. CONTROL_REQ：控制请求

### 6.1 消息说明

外部客户端向 Gateway 发送控制请求，Gateway 根据目标设备 ID 将请求转发给 BCM ECU。

BCM ECU 接收请求后执行对应的车灯控制操作。

### 6.2 控制规则

|项目|设计|
|---|---|
|发送设备|External Client（0x05）|
|目标设备|BCM ECU（0x02）|
|消息类型|CONTROL_REQ（0x02）|
|控制方式|一条消息控制一盏灯|

第一版支持三种车灯：

|字段值|含义|
|---|---|
|LOW_BEAM|近光灯|
|HIGH_BEAM|远光灯|
|POSITION|位置灯|

车灯控制状态：

|字段值|含义|
|---|---|
|ON|开启|
|OFF|关闭|

### 6.3 Payload 定义

|字段|数据类型|含义|
|---|---|---|
|command|String|控制命令|
|light|String|目标车灯|
|state|String|目标状态|

第一版控制命令固定为 `SET_LIGHT`。

### 6.4 消息示例

请求打开近光灯：

```
{
  "src_id": 5,
  "dst_id": 2,
  "msg_type": 2,
  "seq": 1001,
  "payload": {
    "command": "SET_LIGHT",
    "light": "LOW_BEAM",
    "state": "ON"
  }
}
```

## 7. CONTROL_RESP：控制响应

### 7.1 消息说明

BCM ECU 执行控制请求后，必须向外部客户端返回执行结果。

**每一条能够正常识别的 CONTROL_REQ，无论执行成功还是失败，都必须返回 CONTROL_RESP。**

无法解析的 TCP 帧或 JSON 报文不属于该业务响应保证范围。

### 7.2 响应规则

|项目|设计|
|---|---|
|发送设备|BCM ECU（0x02）|
|目标设备|External Client（0x05）|
|消息类型|CONTROL_RESP（0x03）|
|消息序号|复用原 CONTROL_REQ 的 seq|
|返回要求|成功和失败均返回响应|

### 7.3 Payload 定义

|字段|数据类型|含义|
|---|---|---|
|result|String|执行结果|
|error_code|Integer|错误代码|
|message|String|结果描述|

执行结果：

- SUCCESS：执行成功。

- FAILED：执行失败。


### 7.4 错误码定义

|错误码|名称|含义|
|---|---|---|
|0|SUCCESS|执行成功|
|1001|INVALID_PARAMETER|参数错误|
|1002|UNSUPPORTED_COMMAND|不支持的命令|
|1003|UNSUPPORTED_LIGHT|不支持的车灯|
|1004|EXECUTION_FAILED|执行失败|

### 7.5 成功响应示例

```
{
  "src_id": 2,
  "dst_id": 5,
  "msg_type": 3,
  "seq": 1001,
  "payload": {
    "result": "SUCCESS",
    "error_code": 0,
    "message": "Light turned on"
  }
}
```

### 7.6 失败响应示例

```
{
  "src_id": 2,
  "dst_id": 5,
  "msg_type": 3,
  "seq": 1001,
  "payload": {
    "result": "FAILED",
    "error_code": 1003,
    "message": "Unsupported light type"
  }
}
```

## 8. HEARTBEAT：心跳消息

### 8.1 消息说明

心跳消息用于检测 ECU 设备的通信活跃状态。

Power ECU、BCM ECU 和 Cluster ECU 均需要定期向 Gateway 发送心跳。

Gateway 通过记录每个设备最后一次有效心跳的时间，判断设备是否在线。

### 8.2 心跳规则

|项目|设计|
|---|---|
|发送设备|Power、BCM、Cluster ECU|
|接收设备|Gateway（0x04）|
|消息类型|HEARTBEAT（0x04）|
|发送周期|1 秒|
|Payload|空对象 `{}`|

### 8.3 消息示例

Power ECU 向 Gateway 发送心跳：

```
{
  "src_id": 1,
  "dst_id": 4,
  "msg_type": 4,
  "seq": 1,
  "payload": {}
}
```

## 9. 消息序号管理

### 9.1 序号作用

消息序号用于：

1. 识别不同的业务消息。

2. 辅助判断消息的新旧。

3. 辅助发现应用层消息缺失。

4. 匹配 CONTROL_REQ 和 CONTROL_RESP。


### 9.2 序号规则

|项目|规则|
|---|---|
|初始值|1|
|新消息|序号递增 1|
|序号管理|每个发送设备独立维护|
|请求与响应|CONTROL_RESP 复用请求的 seq|

不同设备允许使用相同的序号，需要结合 `src_id` 识别消息来源。

例如：

```
Power ECU：seq = 1001
BCM ECU：seq = 1001
```

两条消息来自不同设备，不属于同一条消息。

TCP 已经保证单连接内字节流的可靠、有序传输，应用层 seq 不替代 TCP 的可靠性机制。

## 10. DeviceManager：设备状态管理

### 10.1 设计目标

Gateway 需要维护各 ECU 的通信状态，及时发现设备异常或失联。

### 10.2 设备状态定义

|状态|含义|
|---|---|
|NOT_CONNECTED|尚未收到首次有效心跳|
|ONLINE|设备通信正常|
|DEGRADED|心跳超时，通信异常|
|OFFLINE|设备已经离线|

### 10.3 状态判断规则

|条件|状态|
|---|---|
|尚未收到首次有效心跳|NOT_CONNECTED|
|收到首次有效心跳|ONLINE|
|距离最后一次有效心跳达到 3 秒|DEGRADED|
|距离最后一次有效心跳达到 6 秒|OFFLINE|
|TCP 连接明确断开|直接 OFFLINE|
|异常后连续收到 2 次有效心跳|恢复 ONLINE|

心跳恢复时，需要连续收到两次有效心跳，不能仅凭一次心跳立即确认恢复。

### 10.4 状态区分

NOT_CONNECTED 与 OFFLINE 的区别：

- NOT_CONNECTED：设备尚未完成首次在线确认。

- OFFLINE：设备曾经接入，但后来确认失去通信。


仅建立 TCP 连接，不代表 ECU 已经正常在线，必须收到有效心跳。

### 10.5 状态变化示意

```
NOT_CONNECTED
      |
      | 首次有效心跳
      v
   ONLINE
      |
      | 3秒无心跳
      v
  DEGRADED
      |
      | 6秒无心跳
      v
   OFFLINE
```

异常恢复：

```
DEGRADED / OFFLINE
        |
        | 连续收到2次有效心跳
        v
      ONLINE
```

## 11. Gateway 消息处理流程

Gateway 的整体业务处理流程：

```
TCP / UART 接收数据
        |
        v
传输协议解析
        |
        v
提取完整业务消息
        |
        v
JSON 解析
        |
        v
MessageValidator
消息合法性校验
        |
        v
MessageRouter
根据 dst_id 进行消息路由
        |
        v
目标 ECU 业务处理
        |
        v
生成响应或执行对应操作
```

各模块职责：

|模块|职责|
|---|---|
|TcpFrameDecoder|TCP 帧解析|
|MessageParser|JSON 消息解析|
|MessageValidator|消息合法性校验|
|MessageRouter|消息路由|
|DeviceManager|设备状态管理|

## 12. 与 M2 TCP 帧协议的关系

M2 阶段已经确定 TCP 帧格式：

```
[4字节正文长度（大端）][JSON正文]
```

其中：

- 前 4 字节表示业务消息正文长度。

- 正文采用 JSON 格式。

- 正文最大长度为 4096 字节。

- 长度字段不包含自身。


例如，业务消息：

```
{"src_id":1,"dst_id":3,"msg_type":1,"seq":1,"payload":{}}
```

经过 TCP 帧封装后，变成：

```
[4字节长度][JSON正文]
```

因此：

**M2 负责 TCP 字节流的帧边界，M3 负责 JSON 正文中的业务含义。**

|CONTROL_RESP|返回控制执行结果|
